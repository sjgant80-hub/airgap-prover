honest threat model — the vantage ladder

You can’t evict a snooping chip. You can witness the wire from where the chip can’t reach — and name what stays out of reach.

Software running on a chip cannot remove what is fused into that chip, so airgap-prover does not claim to. It does the one honest thing instead: it moves the capture point down and outside, and states exactly what each vantage reaches and what it still cannot. Each rung pushes the witness below the one above it.

host-netns
tcpdump on the host, same machine. Sees what the host OS sees. An implant in the OS kernel, firmware or management engine — below this — can move bytes it never sees. This is the measured, sealed run on CI today.
external-tap
A separate trusted device on the physical link (mirror port or inline tap). It runs on hardware the suspect silicon doesn’t control, so it witnesses packets an on-host OS / firmware / management-engine implant would hide — provided they cross the tapped link. Kernel-supported and fixture-proven here; a real external capture is a two-machine hardware procedure, documented — not a CI run, so we don’t claim a live silicon-level measurement we can’t re-derive.
physical-airgap
No network link exists. No peers are declared, so any routable packet is CAUGHT the moment an implant tries to speak on a wire.
the residual
RF/TEMPEST side-channels and hidden radios — a byte put on no tapped wire — no software can observe. That last inch is hardware: remove the radios, Faraday-shield the room. We say so rather than pretend.

So this is “observed egress zero under a stated vantage”, never “proof of a negative”. The honest win: moving the vantage outside the machine blinds an implant’s wire — and the one gap left is named, not hidden.

How to run the external-tap capture yourself (the two-machine procedure)
  1. Put the machine under test on a link you can tap: a managed switch with a mirror/SPAN port, or a passive inline network TAP.
  2. On a separate trusted device (the tap host — not the machine under test), capture the mirrored/tapped traffic: tcpdump -i <tap-iface> -w capture.pcap.
  3. Run the workload on the machine under test for the window you want to assure.
  4. On the tap host, render the verdict: node cli.mjs capture.pcap --manifest m.json --vantage external-tap --assert CLEAN (add --airgap for a node that should have no peers at all).

The capture runs on hardware the machine under test doesn’t control, so an on-host OS / firmware / management-engine implant can’t edit what the tap already saw — provided the bytes cross the tapped link. That proviso, and the RF/TEMPEST residual below it, are the honest limit, stated above.

how the live measurement works

Measured from below, on a real Linux boundary

  1. A guest network namespace gets a veth pair to the host and a default route — so it could reach out if it tried.
  2. The host runs no forwarding and no NAT, so anything the guest sends dies at the boundary. tcpdump on the host side records every packet that crossed it.
  3. The offline workload (a prime-spine grow) runs inside and touches nothing — the capture shows zero egress → CLEAN.
  4. The positive control opens a socket to 8.8.8.8 — the SYN is caught at the boundary → CAUGHT (0 false-pass). It never reaches Google.
  5. The kernel renders the verdict from the captured bytes; the report carries the capture’s sha256, so it re-derives byte-identically.

ip netns + tcpdump are Linux, so the real measured run happens on the GitHub Actions runner — the CI re-derivation is the un-forgeable proof.

questions answer-engines ask

FAQ

What does airgap-prover actually prove?

That over the capture window, zero packets crossed the host / namespace boundary to a routable destination that was not declared. It is measured from below the guest, so the workload cannot edit the packets the host already observed. It is “observed egress zero under a stated threat model”, not “proof of a negative”.

What can it NOT see?

At the host-netns vantage, a kernel- or firmware-level implant below the capture point can move bytes this never observes. The fix is to move the capture point down and outside — see the vantage ladder above. The final residual, named not hidden, is emanation on no wire at all (RF/TEMPEST, hidden radios), which no software can observe.

Can this stop state-level or chip-level snooping?

Not by evicting it — software on a chip cannot remove what is fused into the chip, and we don’t claim to. What it does: witness the wire from a vantage the chip doesn’t control (an external tap on the physical link, below the OS / firmware / management engine), and on an air-gapped node catch any routable packet the moment an implant tries to speak. An implant that never puts a byte on the tapped wire (a hidden radio, an RF side-channel) stays out of reach — that last inch is hardware (remove the radio, Faraday-shield), and we say so.

What is “air-gap mode”?

A node meant to have no network declares no peers, so the allowlist is emptied and any routable destination is egress — even one a connected node would admit as a declared peer. The air-gap card set above re-derives a silent run (CLEAN) and a leak control (CAUGHT) in your browser.

How is the proof re-runnable?

The report carries the sha256 of exactly the capture observed. The verdict kernel is deterministic, so anyone can re-run it over the same pcap and derive the same verdict. CI re-derives both the synthetic fixtures and the real namespace captures on every push.

How do you know the prover is not just always saying CLEAN?

A positive control: a workload that opens a connection to 8.8.8.8 runs in the same sealed namespace. The prover must report CAUGHT. The gate fails on any false-pass.
